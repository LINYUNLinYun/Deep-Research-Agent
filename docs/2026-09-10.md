## 目标

为后续 Policy/Verification Skill 自进化评测固化一份成本受控配置，并用两道 Miner 题验证完整评测链路。不修改 production 默认配置，也不处理 Red-Blue 实现。

## 新增评测 Profile

新增：

- `configs/evaluation/cost_controlled_no_adversarial.yaml`

该文件是可由 `runner.load_config()` 独立加载的完整配置，而不是 YAML 局部覆盖。这样可以避免未来 `configs/default.yaml` 变化导致实验条件静默漂移。

固定条件：

- 所有 LLM 模块使用 `deepseek`；
- temperature 固定为 0，top-p 固定为 1；
- Solver 保留 `thinking=true`，其余模块显式 `thinking=false`；
- 动态模型路由关闭；
- `harness_evolution.enabled=true`；
- 普通运行默认只加载 production Registry；
- Red-Blue `adversarial.enabled=false`；
- Numeric Verification `evidence_verification_enabled=true`；
- `max_verified_claims=10`；
- `max_replan_rounds=1`；
- legacy GRPO evolution 保持关闭；
- live web search 保持开启，正式晋升实验仍应优先使用严格 Replay。

## 隔离和解释边界

- 没有修改 `configs/default.yaml`，普通项目运行行为不变。
- Candidate 不能由该配置隐式加载；paired evaluator 必须显式指定 candidate Registry。
- 关闭 Red-Blue 不会关闭 Numeric Verification Skill。EvidenceVerifier 在 Summarizer 后、Red-Blue 分支前执行。
- `max_rounds=1` 只是防御性保留值；由于 `adversarial.enabled=false`，本 profile 不会调用 Red 或 Blue。
- 该 profile 生成的结果必须标记为 `cost-controlled / no-adversarial`，不能冒充完整系统结果，也不能直接与开启 Red-Blue 的历史结果比较。
- 限制 replan 为 1 是为了避免此前 evidence-gap 导致的三轮整批扩展；它属于固定实验条件，baseline 和 candidate 必须完全一致。

## Smoke Test 暴露的问题

这两题证明流程能运行和追溯，但也说明当前结果还不适合直接扩展成 20 题正式 baseline：

1. 两题初始 DAG 都是全成功，却都因为 Numeric Verification 的证据缺口触发完整 replan。一次 replan 基本重跑整批任务，并再次合成报告，是 69 次 LLM 调用的主要来源。
2. `tech_001` 验证结果为 supported=2、contradicted=7、unknown=1；`med_001` 为 supported=2、contradicted=5、unknown=3。两题 unsupported rate 都是 0.8。需要检查 claim/span 对齐质量，不能直接把 80% 当作真实事实错误率。
3. SearchController 在全局 `search_attempts=10` 后持续返回 `stop_search`，但其他并发 Worker 仍继续发起搜索。最终 backend calls 分别为 33 和 26，说明当前 hard cap 只影响单次响应，未真正阻断整个 session 的后续调用。
4. 两题 `rewritten_queries=0`，production Search Policy 的 rewrite 机制在本次正式轨迹中没有触发。
5. 报告规则指标的 `citation_coverage=0`，但 Markdown 末尾附加了大量来源；说明正文 claim 没有形成可被 evaluator 识别的 inline citation，来源附录不能替代 claim-source 对齐。
6. 两份报告分别约 97KB 和 86KB，大量搜索结果进入参考来源附录。当前 composite 约 0.8 主要由 comprehensiveness、字符串事实匹配和逻辑规则拉高，不能据此判断报告已经达到高质量。
7. Replan 产生了明显的任务漂移样本：医疗题某个子任务输出了 CRISPR 主题，科技题某个子任务切换成 DeepSeek/Qwen/GLM/Kimi 比较。最终 Summarizer 有一定纠偏，但说明累计上下文与重规划任务约束仍不可靠。

结论：评测工程链路验证通过；质量评测与成本控制尚未通过。下列问题已在同日完成代码修复，但还需要新的、严格配对的运行验证后才能决定是否扩到 20 题。该 smoke test 不能证明自进化有效，自进化仍需 production/candidate paired evaluation。

## Smoke 后续修复

本节记录针对上述真实轨迹问题完成的修复。为避免继续产生费用，本轮只做确定性单元/集成测试，没有重新调用 DeepSeek，也没有覆盖前述原始 smoke 产物。

### 1. Search hard cap 改为调用前强制执行

涉及：`src/tools/search_controller.py`。

- provider 调用预算现在在第一个 `await` 前完成检查和预留；共享同一 SearchController 的并发 Worker 无法在检查与计数之间超额占用预算；
- 达到 `max_search_attempts` 后直接返回结构化 `hard_cap_reached=true` 与 `stop_search_requested=true`，不会访问真实搜索 provider；
- policy 的 `search_attempts` 信号改为实际 `backend_calls`，不再把 cache hit 与被阻断请求误算成付费/网络调用；
- rewrite 和 switch-provider 产生的额外 provider 调用也必须占用预算；
- telemetry 新增 `blocked_calls`，区分调用意图与真实 backend call；
- cache hit 仍可读取，但达到上限时会同时要求 Worker 停止继续搜索并进入总结。

确定性测试验证：上限为 2 时，第三个不同 query 会被阻断，fake provider 只收到 2 次调用。

### 2. Evidence gap 改为局部 Verify DAG

涉及：`src/orchestrator/orchestrator.py`、`src/orchestrator/schemas.py`、`src/core/runner.py` 和配置文件。

- EvidenceVerifier 不再只返回 supported/contradicted/unknown 汇总，还返回待处理 claim 的 ID、原文、风险、状态、原因、source refs 与候选 source span；
- 当 unsupported rate 越过阈值时，不再把空的 `failed_tasks=[]` 交给 Planner 重新生成完整 DAG；
- Orchestrator 直接为优先级最高的 contradicted/high-risk claims 创建独立 `TaskType.VERIFY` 小型 DAG；
- Verify 任务强制携带原始研究问题、待核验 claim 和候选原文 URL，并明确要求优先用 browser 打开原文，证据不足必须返回 unknown；
- 原有成功结果进入 historical results，第二次 Summarizer 只增加局部验证证据，不重跑全部研究任务；
- 新增 `planner.evidence_replan_max_tasks` 安全上限：默认 profile 为 3，成本受控 profile 为 2；实际任务数还会受到 unresolved claim 数和 `max_sub_questions` 共同约束；
- 如果没有可执行的 unresolved claim，则跳过 broad replan，不伪造 replan 次数；
- 工具失败导致的普通 replan 仍保留原 Planner 路径，本修复只改变“合成后 evidence gap”分支。

确定性集成测试验证：合成后出现 unsupported claim 时，状态直接进入 `DISPATCHING`，只生成 `verify_gap_r1_1...`，Planner stub 没有 `replan()` 也能成功完成状态转换。

### 3. DAG 依赖证据真正进入 Worker Prompt

涉及：`src/agents/researcher.py`。

- 将 `dep:<task_id>` 对应的成功 AgentResult 显式加入 Worker prompt；
- Compressor 生成的 `compressed_context` 也会加入 prompt；
- Worker 在搜索达到 session hard cap 时，如果已有成功依赖证据，可以基于依赖完成分析，而不会把预算停止误判为空搜索失败；
- 没有依赖证据的根任务仍不能借 hard cap 绕过“事实任务必须使用工具”的约束。

该修复也防止 Analyze/Verify 层在无法继续搜索时退回模型记忆，并修复了此前“运行时 Memory 有依赖、模型 prompt 看不到依赖”的接线缺口。

### 4. Canonical Source Catalog 与有效引用评测

涉及：`src/agents/summarizer.py`、`src/core/runner.py`、`evaluation/metrics/rule_based.py` 和 `evaluation/metrics.py`。

- Summarizer 调用前从真实 tool trajectory 构建稳定编号的 Source Catalog；
- 每个成功子任务最多贡献 4 个不同 URL，目录总量按成功任务数调整并保留 40 条防御性上限，避免单一 Worker 和超长附录淹没上下文；
- Prompt 明确要求数字、日期、比较和因果 claim 使用 `[N]` inline citation，禁止编造不存在的来源 ID，证据不足时应标记 unknown 或删除；
- 模型不再自行生成另一份来源列表，运行时统一追加 canonical catalog；
- `ResearchReport.sources` 与 Prompt 中的编号保持一致；参考附录 snippet 限制为 240 字，避免再次产生 80–100KB 的来源堆积；
- citation coverage 在存在参考目录时只承认能解析到目录条目的 `[N]`，例如正文 `[99]` 而目录只有 `[1]` 时得分为 0；
- 自动生成的“元信息”和“参考来源”部分都不进入 claim paragraph 分母；直接 URL 与显式来源标记仍保持兼容。

注意：这些改动让引用指标更难被伪引用抬高，但不能单靠 Prompt 保证 claim-source entailment。真实 citation coverage、unsupported claim rate 和报告长度变化仍需要实验验证。

### 5. 配置、兼容性与测试

- production 的不可变 Policy/Skill YAML 没有修改；
- production/candidate Registry 指针没有移动；
- `configs/default.yaml` 只新增局部验证任务上限，其他默认行为未切换；
- 成本受控 profile 将局部 Verify 任务固定为最多 2 个；
- 原两题 smoke 结果完整保留，便于修复前后配对比较；
- 新增 hard-cap、局部 Verify DAG、合成状态转换、依赖 prompt、source catalog、非法引用和元信息排除测试；
- 全量回归命令：`PYTHONPATH=. python3 -m pytest -q`。
- 最终结果：63 tests passed；`git diff --check` 通过。

### 发现并修复的确定问题

1. 裸四位数量 `2048` 被年份正则识别成日期，而 `2,048` 被识别成普通数字，导致同值 claim 判错。现在只有带 `年/年度/FY/财年` 标记的四位数才作为日期。
2. 数字正则会把 `2.5 kg` 的 `k`、`2.5 千克` 的 `千` 当作数值倍率，双方可能同时错误归一化为 2500 kg，从而出现“标签正确但归一化错误”的假通过。现在 scale 正则不会吞掉重量单位前缀。
3. 报告引用标记 `[1]` 会被 Numeric Skill 当作 claim 中的额外数字，导致带引用的数字句被系统性误判为 contradicted。现在 Markdown 数字引用标记会从数字事实中排除。
4. `EvidenceVerifier` 的词法阶段只保留一个最佳来源，再把这个单一来源传给 Numeric Skill，使 Skill 在线主线看不到其他相互冲突的来源。现在异步真实路径会把所有可归属来源交给 Skill；有显式引用时仍只传匹配该引用的来源。
5. 离线 evaluator 过去只比较 supported/contradicted/unknown 标签，没有核验 fixture 的 `expected_normalized`，因此无法发现双方一起归一化错误。现在新增 `numeric_normalization_accuracy`，并在逐条记录中保存 `normalization_correct` 与 Skill reason。
6. `mechanism_triggered` 过去按 candidate 分组硬编码；本日后续进一步收紧为：candidate artifact hash 必须与 baseline 不同，且 paired 最终标签必须实际发生变化。同版本或无行为差异的 YAML 不再算作机制触发。

## 第二轮进化前：首批安全 Numeric Primitives 固化

为避免继续通过固定阈值制造有限或虚假的涨点，本轮先人工固化三项无网络、无动态导入、无任意公式执行的安全能力。两名 Luna subagent 分别编写 primitive 契约测试和审计组合管线，另一名审计 Candidate/Registry 安全边界；本轮没有创建新 candidate、没有调用 LLM、没有运行 Held-out、没有移动 production/canary 指针。

### 新增安全能力

1. `align_entity_value`
   - 为每个数字提取有限白名单内的指标概念和 A/B、甲/乙等实体限定词；
   - 比较时要求实体和指标对应，避免“A=100、B=80”与“A=80、B=100”因数字集合相同而误判 supported；
   - 实体缺失或多实体歧义时保守返回 unknown，不使用 fuzzy match 或 LLM 猜测。
2. `convert_measurement_unit`
   - 使用固化换算表支持 g↔kg、m↔km，以及对应中文单位；同时识别吨和摄氏度，但不做汇率或华氏度等未经审核的换算；
   - 缺单位、未知单位和跨维度比较不推断，返回 unknown；
   - 修复 `1000 m` 中小写、带空格的 `m` 被识别为 million scale 的歧义，同时保持大写紧凑 `M` 作为 million。
3. `filter_semantically_irrelevant_numbers`
   - 只有来源数字与 claim 共享固化指标概念时才进入数值比较；
   - “样本量 120”不能反驳“住院率下降 20%”，此类情况返回 unknown；
   - 同一指标的明确错误值仍返回 contradicted。

实现位于 `src/harness_evolution/numeric_primitives.py`，只包含有限实体词表、单位表和纯函数。`NumericVerificationSkill` 只有在 YAML 显式包含新 primitive 时才进入增强比较；production v0001 YAML 不包含它们，因此本轮 Challenge Development 基线仍为 36/48。返回结果新增 `primitive_trace`，用于后续证明候选能力确实执行。
