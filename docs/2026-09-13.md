# 2026-09-13 P-1 链路修复与 Evidence Ledger 落地记录

## 目标与边界

本轮按 `agents-research/agent提点/deepresearch-agent改进策略.md` 的优先级执行：先完成 P-1 六项确定性链路修复，再落地策略一的生产主路径——compression-safe Evidence Ledger、refer-then-claim 合成约束、claim-level verification edge 和定向补证据。

工作基于已有未提交工作树继续，未回退或覆盖无关改动。本轮没有运行付费 live-web/LLM benchmark；“实验结果”均来自确定性回归、离线集成场景和全量测试，因此只能证明机制生效与无回归，不能据此宣称报告质量已经显著提升。

## P-1 修复

### 1. 非 Web 工具不再被误判为零证据

- `src/agents/researcher.py` 新增统一 evidence-key 提取，覆盖 `web_search`、`arxiv_reader`、`browser`、`file_reader`、`calculator`、`code_sandbox`。
- 只有执行 evidence-producing action 且没有新增证据时才累积低 novelty streak；`notepad` 等管理型工具不会误触发总结。
- Browser error/warning 不会被当作有效证据。

### 2. Prompt 与运行时工具预算使用同一个事实源

- System prompt 和 task prompt 都从 `_tool_call_limit()` 渲染，不再硬编码 2 次。
- 默认配置 `max_tool_calls_per_subagent: 6` 现在会真实出现在两层 prompt 中，执行层仍负责最终 hard cap。

### 3. 工具预算耗尽成为受控停止，而非 Worker 失败

- 超过 `max_tool_calls` 返回 `hard_cap_reached + stop_search_requested + error_type=budget` observation。
- 已有证据时要求立即总结；零证据仍 fail closed。
- 避免正常预算边界触发 broad replan 和额外调用。

### 4. Search hard cap 在 Harness Evolution 关闭时仍生效

- `SearchController` 新增永久启用的 `max_backend_calls`；versioned policy 只能进一步收紧上限。
- `configs/default.yaml` 新增 `tools.search_control.max_backend_calls_per_run: 64`。
- Search event 增加 `stage/task_id`，支持区分 worker、verify 和 Blue。

### 5. Blue supplementary search 接入统一 SearchController

- `BlueAgent` 接收共享 `search_controller`，不再优先直连原始 search tool。
- Worker 与 Blue 共享缓存、provider hard cap、去重和 event trace。
- `src/core/runner.py` 从 web-search tool 注入同一个 controller。

### 6. Replan 复用成功任务并携带来源

- Orchestrator 按 `task_type + normalized description + expected_type + search_hints` 生成 task signature。
- 新 DAG 出现完全相同的成功任务时直接复用 `AgentResult`，trajectory 增加 `event=reused`，不再调用 Worker。
- Planner replan context 除 500 字摘要外新增最多 12 个 source URLs，减少证据失忆和主题漂移。

## 策略一：Evidence Ledger 与 refer-then-claim

### 数据合同

- `src/evidence/schemas.py` 新增：
  - `SourceRecord`：稳定 `source_id`、独立来源 cluster、canonical URL、原文 span、日期、retrieval time、content hash、task/tool lineage；
  - `EvidenceBundle`：sources、claims、claim-evidence edges、open questions；
  - `ClaimEvidenceEdge`：`claim_id → source_id → supported/contradicted/unknown`。
- `src/evidence/ledger.py` 新增 `EvidenceLedger`，统一读取 web results、papers、browser full text 和 typed VERIFY evidence。
- `AgentResult.evidence_bundle` 成为正式跨模块字段；Researcher 成功返回时立即物化 bundle，下游优先消费 bundle，同时保留 trajectory 扫描作为旧结果兼容路径。

### Compression-safe provenance

- Orchestrator 在任何 L3 compression 之前从 canonical trajectories 冻结 source catalog。
- Summarizer 使用压缩后的模型上下文，但使用压缩前 catalog；即使多个结果被聚合成无 trajectory 的 `compressed_evidence`，来源仍保留。
- Browser tool call 的 args 被保存在 trajectory，因此纯文本正文能重新绑定原 URL。

### 受约束合成和核验

- Summarizer 不再强制 3000 中文字/2000 英文词，长度由已有证据决定。
- Prompt 改为 refer-then-claim：先选择精确 span/catalog ID，再写一个受支持的 atomic sentence，并把 `[N]` 紧邻事实句。
- Source Catalog 给出 stable source ID 和更长 evidence span；模型不能自行创造引用 ID。
- EvidenceVerifier 现在识别显式 `citation_id` 和 `source_id`，最终报告持久化 `claim_evidence_edges` 与 `open_questions`。
- VERIFY task 强制 JSON contract；`supported` 没有非空 URL+span 时自动降级为 `unknown`。
- 证据缺口 replan 不再被 retrieval low-novelty gate 抑制；下一轮合成收到 prior verified draft，只修改新证据涉及的 claim，降低整篇漂移。

## 回归与实验结果

### 定向机制实验

| 场景 | 结果 | 证明的机制 |
|---|---:|---|
| `arxiv_reader → browser → summary` | 2 个非 Web evidence calls，0 次 false evidence-gain stop | 非 Web 工具不会一轮后被强制总结 |
| Prompt budget=6 | system/task prompt 均为 6，未出现 `AT MOST 2` | prompt/runtime budget 对齐 |
| Worker 工具预算=1 | 第 2 次调用被转为 budget stop，最终为 SUCCESS summary | 预算边界不再误报 FAILED/replan |
| 无 evolution policy，backend cap=1 | provider 实际调用 1 次，第 2 个不同 query 被 hard-block | 普通运行仍有 session hard cap |
| Worker/Blue 共享 cap=1 | Blue provider 调用 1 次，第 2 次 hard-block；2 个 event 均标 `stage=blue` | Blue 不再绕过预算与 trace |
| Replan 出现相同 task signature | Worker 新调用 0 次，返回 trajectory `event=reused` | 成功任务不重复执行 |
| 强制多结果聚合 compression | 压缩前 2 个 sources，最终仍保留 2/2 URLs | L3 不再吞掉引用目录 |
| Browser URL 带 `utm_source` | canonical URL 去 tracking 参数，full span/hash/source ID 均保留 | Browser 正文成为一等证据 |
| Citation ID=7 + stable source ID | verifier 判 supported，edge 指向 `src_stats` | 引用编号不再只依赖列表位置 |
| VERIFY 声称 supported 但无 span | 自动降级 unknown | typed verification fail closed |

## 当前结论

P-1 六项机制已由回归测试覆盖，策略一的 ledger → compression-safe catalog → refer-then-claim → claim-edge audit → targeted verify 主路径已经接通。当前证据证明结构和控制流按预期工作，并且现有 141 项测试没有回归。

尚未完成的是有统计意义的 live quality ablation。下一步应冻结同一批 web fixtures，在 baseline/candidate 上比较 citation correctness、citation completeness、unsupported high-risk claims、source retention、supported claims/backend call 和 token/cost；至少 21 个 query、3 seeds、按 query 聚类 bootstrap 后，才能下“真实涨点”的结论。

## Live 配对质量验证（12 题 miner，单次运行）

随后使用 ResearchBench v1 miner 的同 12 道题完成了一次改进前后配对验证：

- baseline：`outputs/evaluation/baseline-no-numeric-miner-v1`
- candidate：`outputs/evaluation/strategy1-current-no-numeric-miner-v1`
- 两组的配置哈希均为 `f465add8d587aab2e6e3028f59935a47d7bee030d51c5aa9d78c5137eb0185fc`
- 模型均为 `deepseek-v4-flash`，temperature=0；Red-Blue 和 Numeric Verification 均关闭
- dataset、split、registry、evaluator 标识与采样参数一致；搜索为 live，未冻结 fixture

结果：

| 指标 | Baseline | Candidate | 差值 |
|---|---:|---:|---:|
| Composite | 0.8767 | 0.8301 | -0.0466（-5.31%） |
| Citation coverage | 0.6344 | 0.4688 | -0.1656 |
| Factual accuracy | 0.8194 | 0.7639 | -0.0556 |
| Comprehensiveness | 0.9881 | 0.9881 | 0.0000 |
| Logical consistency | 0.9994 | 1.0000 | +0.0006 |
| Bias proxy | 0.9843 | 0.9858 | +0.0016 |
| 平均耗时 | 64.82s | 61.56s | -3.26s |

- 逐题胜负：4 胜 / 8 负。
- 配对 mean delta 的 50,000 次 bootstrap 95% CI：`[-0.0848, -0.0072]`。
- 配对效应量 Cohen's dz：`-0.647`。
- baseline 平均 21.0 条参考来源，candidate 平均 39.25 条；但引用覆盖反而下降。
- Search decision trace 从每题 16.17 增至 27.92，`stop_search` 从每题 6.67 增至 19.08。

### 诊断

1. `max_backend_calls_per_run=64` 对 7–8 个并行任务加一次 replan 明显过紧。运行日志中出现大量全局 hard-cap，部分重规划层 0 个任务成功，事实覆盖随之下降。
2. Orchestrator 直接调用 `EvidenceLedger().catalog(...)`，绕过 Summarizer `_collect_sources()` 的 40 条上限。实际报告平均来源从 21 增到 39.25；合成 prompt 多次达到约 12k–17.5k tokens，并出现 35k 字符截断。
3. refer-then-claim 目前只是 prompt 软约束。模型仍输出大量无 `[N]` 的表格、列表、分析段，未形成结构化生成或 post-check/rewrite 闭环，因此引用覆盖下降 16.6 个百分点。
4. Ledger 当前追求“收全”，缺少 source-quality/rerank/claim-coverage selection；低质量聚合页、PPT 下载页和重复来源占用上下文，增加来源数量但没有转化为支持密度。

### 结论

本轮没有验证出涨点，反而发现一个中等效应的质量回归。由于两次运行使用 live 搜索且不是同一时刻，本结果不能把全部差值严格归因于本次代码；但 12 个同题配对、相同配置/模型/evaluator 下的负向 CI，以及运行日志中的 hard-cap、上下文截断和未引用段落，足以否决当前版本直接晋级。下一轮应先修复搜索预算分层、catalog token budget/质量筛选、claim-level 引用 post-check，再用冻结 fixtures 做 baseline/candidate 复验。

## 策略二 Phase A：ResearchStateGraph shadow controller

### 状态与控制契约

- 新增 `src/planner/research_state.py`：
  - `FacetState`、`ClaimState`、`OpenQuestionState`；
  - 受限 `FrontierAction`：`search_new_facet`、`deepen_claim`、`open_primary_source`、`cross_validate`、`resolve_conflict`、`stop`；
  - 透明 value components、确定性 tie-break、动作/连续次数预算；
  - critical facet、high-risk support、critical conflict、marginal value 四条件 stop gate；
  - 预算耗尽时 `should_stop=true` 但 `complete=false`，保留 coverage map 与 unresolved questions；
  - 完整 JSON round-trip，支持同状态重放同一选择。
- `SubTask` 新增可选 `facet_id`、`claim_ids`、`completion_criteria`、`risk_question`，旧 plan/fixture 无需修改。
- Planner shadow 开启时要求 facet metadata，但不增加 task 数与预算；共享 `facet_id` 的多个 DAG task 在 graph 中合并为一个上层 facet。

### Orchestrator shadow 集成

- 初始 planning 后构建 graph；replan 只扩展新 facet/claim/question，不丢失 episode 状态。
- 每个 DAG layer barrier 后更新 facet coverage、平均支持度和独立 source cluster 数。
- `decision_trace` 写入 `research_state_initialized` 和 `frontier_shadow`，后者包含全部候选分项、选择、estimated value 与 stop gate。
- Shadow 决策不 commit、不消耗预算、不改变 DAG、不增加搜索调用。
- SearchController event 新增 `facet_id`、`claim_ids`、`source_cluster_ids`、`action`、`estimated_value`。
- `ResearchReport` 和 harness telemetry 持久化最终 research-state snapshot。
- CLI 可用 `--research-state-shadow` 显式打开；默认关闭。

### 先消除策略一对策略二的干扰

- run-level provider cap 从 64 调整到 128，避免 7–8 个并行任务加 replan 被过早饿死；hard cap 仍永久存在。
- 模型侧 catalog 与 lossless ledger 分离：最多 24 条且最多 12,000 字符，每条 span 最多 500 字符，优先权威/有原文来源并重新连续编号。
- Orchestrator 不再绕过 Summarizer 的 catalog bounds；compression-safe provenance 仍在压缩前冻结。
