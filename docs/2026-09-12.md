## Critic-Repairer 跨轮事务与 Critic 局部重试

### 修复内容

1. 对抗循环增加最后已接受版本的事务语义：
   - 保存 `best_report`、`best_score` 和已接受轮数；
   - 后续 Critic、Repairer 或 post-fix Critic 失败时，不再把此前成功提交的修改错误作废；
   - 有已接受轮时返回最后已接受报告，状态记为 `partial`，并保留对应 `final_score`；
   - 没有成功轮时仍保持原有 fail-closed 行为；
   - history 增加 `fallback_to_best` 和 `accepted_rounds`，便于区分整轮失败与回退到已接受版本；
   - post-fix 分数除与本轮 pre-fix 分数比较外，也不能低于此前最佳分数。

2. Critic 增加单维度 JSON 解析重试：
   - 默认 `critic_dimension_parse_retries=1`，范围限制为 0–3；
   - 只有模型返回内容无法解析时才重试当前维度；
   - 后端和传输错误不重试，避免故障调用放大；
   - 其他已经成功的维度不会重新执行；
   - `CriticVerdict` 和对抗 history 新增 `retry_stats` / `critic_retry_stats`，记录 attempted、recovered 和 exhausted。

## Repairer issue-centered context

### 实现

Repairer 不再对所有 issue 统一发送同一份报告 head/tail，而是为每条问题构造独立 `IssueContext`：

- 定位优先级为：引号内完整 claim 精确匹配 → Markdown 章节匹配 → 引用编号匹配 → 最长公共片段模糊匹配 → head/tail 安全降级；
- 对 Critic 常见的模型化 location（例如“执行摘要及 2.2 节苹果侧”）识别章节编号，并用模糊标题匹配定位真实 Markdown 章节；
- 上下文包由报告开头、目标前文、`<TARGET>` 目标区域、目标后文和报告结尾组成，总长度仍受 `repairer_context_chars` 限制；
- 目标段落涉及的引用 ID 会优先排列在 sources prompt 中，同时保持原始引用编号；
- In-place、Supplementary Search 和 Removal 统一使用该上下文；
- before/after patch 必须位于目标区域，且 before 在完整报告中只能唯一出现；目标外修改和歧义修改直接拒绝；
- 论文书名号标题不再作为正文 claim 锚点，定位范围截止于“元信息/参考来源”之前，避免 Repairer 错误修改来源附录；
- 定位方式和置信度写入 FixOperation detail，如 `heading:0.85`、`exact_claim:1.00`，便于分析失败原因；
- 定位失败时保留正文范围内的 head/tail fallback，不会因为 Critic location 不规范而完全禁用修复。

同时继续保留 patch-first 协议和 self-verify 逐项事务，不允许 issue-centered context 绕过现有安全回滚。
