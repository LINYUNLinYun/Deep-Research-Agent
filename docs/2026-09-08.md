# 2026-09-08 变更记录

## 目标

将 DeepResearch Agent 从依赖固定 heuristic 的原型，改造成具备可观测、可消融、可动态决策能力的 Harness 项目。本次工作集中在工程控制层，不涉及模型训练或后训练。

## 变更摘要

本次完成了三项主改造：

1. SearchController：query rewrite、跨 Agent 搜索去重、session cache 和 evidence novelty。
2. Claim-Level Evidence Verification：建立 Claim–Evidence 结构，支持 `supported / contradicted / unknown` 验证闭环。
3. Dynamic Replan：根据失败比例、依赖影响、证据质量、新颖度和剩余预算决定是否补搜、验证、合成或终止。

同时修复了 DAG 数据传递、工具可靠性、Memory 隔离、上下文压缩、Red-Blue、模型路由和 Evaluation 中的确定性问题。

## 1. Orchestrator、Planner 与 DAG

- DAG 每个执行层结束后立即把结果写入运行时 Memory，下游任务现在可以读取上游结果。
- 上游依赖失败或缺失时，下游任务直接短路，不再继续消耗工具和模型预算。
- Planner 严格拒绝空 `task_id`、重复 `task_id` 和不存在的 dependency。
- Replan 不再由“任意任务失败”触发，改为综合判断：
  - 失败比例；
  - 失败节点是否影响下游；
  - 成功证据是否可用；
  - 新一轮证据是否有增量；
  - token/replan 预算是否充足。
- Replan 接收所有历史成功结果，不再只看到当前轮。
- 成功结果保留阈值根据当前置信度分布动态计算。
- 全局超时后使用已有成功证据生成降级报告，并记录 `force_synthesize` 决策。
- 修复 Summarizer 借用 analyze pool 后导致的 Agent 泄漏。
- 修复 AgentPool 将 analyze/verify Agent 错误释放到 search pool 的统计漂移。

## 3. Evidence Verification 与 Red-Blue

新增结构化对象：

- `Claim`
- `Evidence`
- `VerificationResult`
- `VerificationStatus`

EvidenceVerifier 会优先提取数字、日期、比较和因果类高风险 claim，并根据引用、来源 span、关键词覆盖、数字一致性和否定关系给出保守判断。没有来源原文时不会判为 supported。

主链行为：

- Summarizer 完成后执行 claim-level verification；
- unsupported rate 超过阈值时可以触发新的 verify/replan；
- 验证结果写入 `ResearchReport.evidence` 和 `evidence_verification`；
- 验证结果会校准报告置信度。

Red-Blue 修复：

- 使用报告头尾 excerpt，降低只检查开头的问题；
- Blue 修改长报告时保护未展示的正文，避免用前 4000 字覆盖全文；
- 修复 `_self_verify()` 缺少 `Dimension` 导入导致的 `NameError`；
- Blue 修复后重新运行 Red 评分，确保 `final_score` 对应最终正文；
- issue fingerprint 归一化，允许识别轻微改写后的重复问题。

## 4. Memory 与 Context Compression

Memory：

- 空 `session_id` 自动生成隔离 session，不再默认读取所有历史会话。
- Evaluation 每道题使用独立 session，避免跨题证据泄漏。
- 去重、冲突、检索 top-k、min similarity、淘汰间隔和时间衰减均由 YAML 注入。
- 自动 eviction 已接入写入路径。
- Memory metadata 保存来源、verification status 和 token usage。
- 检索根据 query 长度和 Memory 密度动态调整候选数量与阈值，并增加来源多样性约束。

Compression：

- Compressor 接入 Worker context 和 Summarizer 输入主线。
- 修复 L1 在超预算时降低阈值、反而保留更多文本的方向错误。
- L1 改为按相关性排序并在预算内 rank-and-pack。
- 压缩开关、三级触发阈值和字符/token 比已接入配置。
- `no_compressor` 消融会真正关闭 Compressor。

### Red-Blue 实测 failure mode

本次 live pilot 暴露出确定性的对抗阶段预算失控：

1. Red 每轮固定执行 5 个维度的 LLM 检查。
2. Red 返回的问题数量缺少合理的全局上限和有效去重。
3. Blue 按 issue 串行执行修复，并对每项修复调用 `_self_verify()`，因此单轮可能形成接近 `2 × issue_count` 的 LLM 调用。
4. `med_001` 和 `fin_001` 分别执行了 75、86 次 Blue 调用；多次响应达到 4096 token 截断。
5. 两题最终均因 Blue 返回内容/JSON 不符合预期而将整个 adversarial flow 标为 `SKIPPED`，`adversarial_rounds=0`。即大量修复成本已经发生，但没有形成被主流程接受的对抗结果。
6. 配置中的 `global_timeout_seconds=600` 没有覆盖完整 adversarial 阶段：两题总耗时分别达到 1260.6 秒和 1053.5 秒。
7. `tech_001` 的 Red 有两个维度返回无效 JSON，Red-Blue 在 Blue 执行前直接跳过。
8. Solver thinking 还出现过一次 4096 completion token 全部用于 reasoning、最终正文为空的情况。

### 代码 Review：调用爆炸的确定性根因

本节是在 live pilot 后对 `src/adversarial/` 和 Orchestrator 接线进行的静态复核；以下均可由当前代码确认，不是实验推测。

1. **Red 固定串行调用五个维度**：`RedAgent.attack()` 遍历 `DIMENSION_PROMPTS`，事实、幻觉、逻辑、来源和覆盖各调用一次 LLM。注释写有“并行”，实际实现是顺序循环。
2. **Red issue 无上限且不做当前轮去重**：五个维度返回的全部 issue 直接通过 `all_issues.extend(issues)` 合并。没有单维度上限、全局上限、minor 过滤或跨维度 fingerprint 去重。
3. **Blue 对全部 issue 逐项执行**：排序仅改变顺序，不会截取 Top-K。每个 issue 最多触发一次修复和一次 `_self_verify()`。
4. **外层轮数不等于调用预算**：单轮调用量近似为 `5 Red + N Blue fix + N Blue self-verify + 5 post-fix Red = 10 + 2N`。若 Red 产生 50 个 issue，单轮即可接近 110 次 LLM 调用；`max_rounds=1` 仍不能控制这个问题。
5. **`max_verified_claims` 与 Blue 无关**：`adversarial.max_verified_claims` 只传给独立 `EvidenceVerifier`，不会限制 Red Verdict 或 Blue operations，不能用它作为 Red-Blue 的止损开关。
6. **失败后继续付费执行**：单个修复返回 `success=false` 时，Blue 只把 `self.status` 设为 `failed`，但不 break/return；self-verify JSON 失败也只是标记失败，仍继续剩余 issue。直到整批结束，AdversarialLoop 才检查状态。
7. **一个失败会丢弃整批成果**：Blue 最终状态只要不是 success，Loop 就返回原报告、空 history 并标记 `SKIPPED`。此前成功执行的 patch、调用与自检不会形成可用结果。
8. **Prompt 与实际上下文冲突**：Blue 要求模型返回“完整报告”，实际只向模型提供约 4000 字头尾 excerpt。长报告容易生成不完整全文、无法锚定 patch 或截断 JSON。
9. **Blue JSON 容错弱于 Red**：Red 有常见 JSON 错误修复；Blue fix/self-verify 主要依赖直接 `json.loads` 和简单代码块/大括号提取。输出被截断时通常无法恢复。
10. **Red 的模块级 token 配置没有真正生效**：Runner 使用 `RedAgent(policy=red_policy)`，未传入 YAML 中的模块 `max_tokens`；RedAgent 默认 2048，并在调用时临时覆盖 policy。因此 effective config 虽写 4096，实际日志仍为 2048。
11. **全局 timeout 只在状态切换前检查**：Orchestrator 进入 `_do_adversarial()` 后直接等待整个 `adversarial_loop.run()`，没有用剩余 wall-clock 包裹 `asyncio.wait_for()`，所以 600 秒不能中断正在运行的 Blue。
12. **对抗成本统计失真**：只有成功写入 history 的轮次才累计 `adversarial_rounds`。大量调用后失败会显示为 0 轮，掩盖真实 attempted calls、token 和费用。

关键代码位置：

- `src/adversarial/red_agent.py:298-345`：五维度调用和无限 issue 合并；
- `src/adversarial/red_agent.py:455-499`：issue 解析无数量限制；
- `src/adversarial/blue_agent.py:209-247`：全量排序、逐项修复、逐项 self-verify、失败后继续；

- `src/core/runner.py:330-346`：Red/Blue 初始化与 EvidenceVerifier `max_claims` 的独立作用域。

这不是合理的“Deep Research 正常调用量”，而是缺少端到端预算约束、issue budget 和失败降级策略造成的 Harness failure mode。当前结果支持以下判断：

- Red-Blue 必须增加每轮/每报告 issue hard cap；
- 优先按严重度与证据风险排序，只修复 Top-K；
- 将多个同类 issue 批量修复，避免逐项重复传入整篇报告；
- 对 Red/Blue JSON 做结构化输出约束和有限重试，失败时保留已验证的局部操作；
- 把 adversarial 阶段纳入全局 wall-clock、token、LLM-call 和成本预算；
- 达到边际收益阈值、连续格式失败或截断率过高时提前停止；
- 记录 `attempted_blue_calls`、`accepted_fixes`、`discarded_fixes` 和 post-fix score，避免 `adversarial_rounds=0` 掩盖已经发生的成本。

### 建议修复路线

建议将 Red-Blue 作为独立 Harness 改造处理，不和 Policy/Skill 自进化的首次 paired evaluation 混在同一实验里。

第一阶段先实现安全止损：

- 新增 `max_issues_per_round=5`，仅保留 Critical/Major Top-K；
- 对 issue 做规范化 fingerprint 去重，minor issue 默认只记录不自动修复；
- 新增 `max_adversarial_llm_calls`、`max_adversarial_tokens`、`adversarial_timeout_seconds` 和连续失败 hard cap；
- `_do_adversarial()` 使用剩余全局 wall-clock 执行 `asyncio.wait_for()`；
- 修复失败或 self-verify 解析失败后立即停止当前批次，不再继续消费剩余 issue；
- 将 RedAgent/BlueAgent 的 token 上限由 YAML 显式注入，确保 effective config 与运行行为一致。

第二阶段改造修复协议：

- 按 dimension/fix type 合并同类 issue，一次批量修复；
- Blue 只输出小型 `edits[{before, after, reason}]` patch，不再返回整篇报告；
- 对一批 edits 只做一次 self-verify；
- 使用严格 JSON Schema/structured output；非法或截断输出最多重试一次；
- patch 逐项验证和提交，保留已成功的局部修改，后续失败不能回滚全部结果；
- 来源/覆盖类 issue 分流给 search/replan，Blue 主要处理可定位的事实修正与删除。

第三阶段加入收益控制与可观测性：

- post-fix 只复评受影响维度，避免固定再调用全部五个 Red evaluator；
- 追踪 score delta、accepted fixes、截断率和单位调用收益；边际收益不足时停止；
- telemetry 增加 `red_calls`、`issues_raw/deduped/selected`、`blue_fix_calls`、`self_verify_calls`、`accepted/discarded_fixes`、`truncated_responses`、token、latency 和估算成本；
- 独立做 `no_adversarial / old_adversarial / bounded_adversarial` paired ablation，确认质量收益大于成本后再恢复默认开启。

受控设计下，一轮目标调用量应从当前可达的 `10 + 2N` 限制到约 3～12 次：Red 可先保留五维检查，Blue 将 Top-K 合并为一次修复和一次自检；进一步只复评受影响维度。

### 评测决策

Red-Blue 修复前，后续 Policy/Skill 自进化评测默认使用独立实验配置关闭：

```yaml
adversarial:
  enabled: false
  evidence_verification_enabled: true
```

关闭 `adversarial.enabled` 不会关闭 Numeric Verification Skill：EvidenceVerifier 在 Summarizer 后、进入 Red-Blue 分支前独立运行。为限制证据缺口导致的整批 replan，首次成本受控 pilot 还应将 `orchestrator.max_replan_rounds` 限制为 1。

该实验必须标记为 `cost-controlled / no-adversarial paired evaluation`，不能冒充完整系统结果，也不能与启用 Red-Blue 的作者历史结果直接横向比较。今日按用户决定暂不继续评测，待后续显式启动。
