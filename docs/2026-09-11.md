# 2026-09-11 变更记录

## Agent 自进化代码审查与安全修复

本轮审查覆盖当前离线 Harness 自进化主线、Legacy GRPO 骨架、生产接线、消融评测和相关测试。重点检查了候选隔离、严格 Replay、Promotion Gate、held-out 数据边界和版本晋升完整性。

### 1. 晋升链路改为 fail closed

`VersionRegistry.promote` 不再接受缺少 `decision_sha256` 的最小 JSON。正式晋升现在必须同时满足：

- decision canonical hash 有效；
- `eligible=true` 且所有 Gate 明确通过；
- decision 来自 `held_out`；
- dataset、evaluator 和公开 evaluation artifact 的 SHA-256 完整；
- evaluation 文件仍存在且内容 hash 未变化；
- 存在有效、未变化且 eligible 的 Development 前置决策；
- track 与 artifact 类型一致；
- baseline、candidate 版本和 hash 与当前 Registry 一致；
- candidate parent 仍是当前 production，拒绝 stale candidate。

这项修改会使旧的、缺少完整 traceability 的手写 decision 无法晋升。历史 artifact 和 Registry 指针没有在本轮移动。

### 2. 外部 results 与候选身份绑定

`run_harness_evolution.py evaluate --results` 现在要求输入结果携带 baseline/candidate artifact ID、version、SHA-256，以及当前 evaluator SHA-256。若 candidate Registry 在实验后移动，旧结果不能再被绑定到新 candidate。

Evaluator hash 的代码集合新增 `evaluation/metrics/rule_based.py`，确保 factuality 指标实现变化会强制 Development/Held-out 重跑。

### 3. Strict Replay 覆盖 Repairer Agent

此前 `attach_replay_tools` 只替换 `modules["tools"]` 和 AgentPool factory，但 Repairer Agent 在初始化阶段已缓存原始搜索工具，supplementary search 可以绕开 fixture。

本轮同步替换：

- Repairer Agent 的工具列表；
- Repairer Agent 缓存的 `_search_tool`；
- supplementary search 改为关键字参数调用，与 Replay adapter 接口一致。

未覆盖的 Repairer supplementary request 现在会产生 `ReplayMismatchError`，不能再使用 fixture 外 mock 结果影响 paired evaluation。

### 4. Policy factuality safety metric

Policy 轨道不再写死 `false_supported_rate=0`。本轮采用以下可审计定义：

```text
false_supported_rate = contradicted_claims / total_extracted_claims
```

生成报告中的 factual claim 是系统作出的断言；EvidenceVerifier 判为 `contradicted` 的 claim 计为 false-supported assertion。若主研究流程没有触发 EvidenceVerifier，Policy replay 会在报告完成后独立运行一次 deterministic claim verification。

以下情况不会写入该指标，Promotion Gate 会按缺失指标拒绝晋升：

- EvidenceVerifier 不可用或执行失败；
- 没有抽取到 factual claim；
- summary 计数非法。

该指标基于冻结来源和规则式 EvidenceVerifier，不等价于人工事实核验或独立 LLM Judge。正式扩展前仍应抽样人工审计 contradicted/supported confusion matrix。

### 5. Promotion 统计去伪重复

同一道 query 的多次 repeat 不再作为独立 bootstrap 样本。Promotion Gate 会先按 `query_id` 聚合 paired quality delta，再计算：

- bootstrap confidence interval；
- non-regression rate；
- win/tie/loss；
- paired Cohen's dz。

增加 repeats 现在只能降低单题运行噪声，不能直接放大统计样本量。

### 6. Legacy Evolution 明确降级为数据准备骨架

- Reward 从错误的 `composite * 2 - 1` 修正为 `composite / 5 - 1`；
- `run_evolution.py` 读取配置中的 `training:`，同时保留旧 `trainer:` alias；
- 未接入 GRPO trainer 时命令默认 fail-fast；
- 只有显式传入 `--prepare-data-only` 才运行轨迹、评分和 parquet 准备；
- 不再创建伪 checkpoint 目录，也不再输出“自进化训练完成”。

Legacy 路径仍没有真正更新模型权重，不能作为已经实现的在线自进化能力。

### 7. 消融与测试工程

- 从默认模块消融中删除没有实际执行差异的 `no_evolution`；
- Harness 专项消融增加 `no_harness_evolution`；
- `pyproject.toml` 增加 pytest `pythonpath` 和 `testpaths`，仓库根目录可直接运行 `pytest`；
- 新增晋升防绕过、Development 禁止直升、导入结果身份、Repairer Replay、缺失 factuality 指标、repeat 聚类和 reward 映射回归测试。

## Critic-Repairer 对抗代码审查与修复

针对 2026-09-08 live pilot 中 Repairer Agent 单题产生 75/86 次调用、运行约 17–21 分钟，最终又因输出截断或 JSON 失败而整轮丢弃的问题，本轮完成以下修复：

- 默认最大对抗轮数从 10 收紧为 3，并增加 `max_issues_per_round=5`；Critic 对跨维度结果按位置、维度和修复类型去重，再按严重度/修复优先级选 Top-K，Repairer 入口再次防御性去重和封顶；
- 增加 Critic 原始、去重后、最终选中 issue 数量统计，避免只看到最终列表而无法解释调用放大；
- Repairer 改为逐 issue 事务修复：每项修复前保留快照，自检通过后才提交；修复、自检或后端失败会回滚当前项并停止，不再继续消耗调用；此前已经验证的修复保留；
- 被 self-verify 回滚的 FixOperation 会改为 `success=false`，不再错误计入 resolved；
- 长报告修复若既不是完整报告，也没有可应用的显式 patch，现在会 fail closed，不再把“未产生有效变化”记录为成功；
- 对局部成功的 Repairer 结果执行一次 post-fix Critic 重评分，通过后以 `partial` 状态保留；若 Repairer 首项即失败，或 post-fix Critic 失败，则保留原报告并记录 attempted/discarded round，不再把昂贵尝试伪装成 `rounds=0`；
- 每轮历史新增 `accepted` 和 `outcome` 字段，区分成功、局部成功、失败和丢弃；
- 对抗阶段新增 180 秒独立硬超时，同时取全局剩余时间的较小值；同步 policy 请求移出事件循环，使外层超时能按时取消后续对抗步骤并保留原始报告（超时瞬间已发出的单次请求仍由模型后端自身的请求超时回收）；
- Critic/Repairer 的 `max_tokens` 和单轮 issue 上限现在由配置显式注入。

按默认配置，单个完整对抗轮的模型调用理论上限由原来的随 issue 数无界增长，收敛为 `5 次 Critic + 2×5 次 Repairer + 5 次 post-fix Critic = 20 次`，并进一步受 3 轮和 180 秒硬边界约束。这仍是上限而非成本目标，后续 live pilot 应继续观察实际调用分布。

新增回归测试覆盖：Critic 去重/Top-K、Repairer 当前项回滚与已验证项保留、局部成功结果重评分保留，以及 Orchestrator 对抗阶段硬超时。

### 真实后端 smoke test

使用一条故意写错的短报告进行受限 live smoke（`max_rounds=1`、`max_issues=1`，无搜索调用）：报告声称标准大气压下水的沸点为 `90 °C (363.15 K)`，随附 NIST 来源片段给出 `100 °C (373.15 K)`。

- 默认 Critic/Repairer 后端 MiMo 在第一次 Critic 请求即返回 `401 Invalid API Key`。系统正确 fail closed，Repairer 调用为 0、报告未被修改；当前 MiMo 凭证需要在仓库外更新。
- 使用已配置的 DeepSeek 后端、未显式关闭 thinking 时，前两个维度正常，但 logical 维度将 2048 completion tokens 全部消耗在 reasoning，返回正文为空，Critic 正确 fail closed。
- 使用 DeepSeek 且 `thinking=false` 时，完整 Critic → Repairer → self-verify → post-fix Critic 链路在 14.10 秒内成功：Critic 10 次调用、Repairer 2 次调用，报告修正为 `100 °C (373.15 K)`，评分从 0.225 提升至 9.925，history 标记 `accepted=true`、`outcome=success`。

据此将 Critic/Repairer 模块采样配置显式设为 `thinking: false`。这解决严格 JSON 被 reasoning token 挤空的问题，但不解决 MiMo 的无效 API Key。

由于 MiMo live smoke 返回 `401 Invalid API Key`，默认 Critic/Repairer backend 暂时从 MiMo 切换为已实测通过的 DeepSeek；Critic/Repairer 继续强制 `thinking=false`。Planner、Solver、Summarizer、Judge 和 Compressor 的后端映射未随之调整。MiMo 凭证恢复后必须先通过同一 live smoke，才能切回默认对抗后端。

### Baseline × Critic-Repairer 第一阶段配对实验

新增 `scripts/run_critic_repairer_report_ablation.py`，直接读取此前保存的 Baseline 报告，对原文和 Critic-Repairer 副本使用当前 ResearchBench evaluator 做配对评分。入口逐题原子保存 results、候选报告和完整 history，并支持 `--resume`。

第一轮 `stage1-v1` 暴露真实长报告协议问题：5 题 Critic JSON 失败、1 题 Repairer 长报告补丁无法合并。修复包括：

- Critic Prompt 每维度最多输出 2 个最高优先级 issue，而不是生成完所有问题后才 Top-K；
- Critic 输出预算调整为 4096，并向 Critic/Repairer 提供报告中的全部 20 条来源；
- Repairer 长报告改为 patch-first 协议，`changes/removed_segments` 必须先返回精确原文，`fixed_content` 可为空且置于 JSON 最后；
- self-verify 支持 Markdown fenced JSON；
- Critic 失败轮也保留 history；
- post-fix Critic 分数下降时整轮拒绝，失败修复不进入 resolved 状态。

最终干净实验 `redblue-baseline-stage1-v4` 使用 4 个低分样本和 2 个高分 guardrail：

- Baseline / Critic-Repairer 平均 Composite 均为 0.833569；
- Win/Tie/Loss = 0/6/0，平均 paired delta = 0；
- 只有 `tech_003` 保留了经验证的谨慎化措辞，状态为 partial，Critic 自评分 5.6 → 5.6；
- 其余 5 题候选均被 self-verify 回滚，无报告和规则指标回归；
- 共调用 Critic 35 次、Repairer 15 次，对抗阶段累计 137.56 秒。

本阶段不能证明 Critic-Repairer 带来可测质量收益；只能确认真实长报告上的 fail-closed 和回滚保护有效。扩大到 21 题前，应先补强 supplementary search 的来源/引用绑定、Removal 后句法修复，以及独立盲审或 claim-level factual evaluator。

产物：`outputs/evaluation/redblue-baseline-stage1-v4/results.json`、`summary.md`、`reports/` 和 `history/`。失败的 v1/v2/v3 产物保留用于协议回归审计，不能与 v4 混合作为效果统计。

### Repairer 有效修复率改进

针对 stage1-v4 中 Repairer 候选大量被回滚、6 题只有 1 题最终修改的问题，本轮改进了修复协议和执行策略：

- 单项候选失败或 self-verify 否决时只回滚当前事务并继续下一项；只有连续失败达到 `max_consecutive_failures=2` 才熔断，后端/传输异常仍立即停止，避免故障调用放大；
- 每轮记录 `repairer_repair_stats`，包含 selected、attempted、committed、rolled_back 和 failure-cap 后跳过数，后续不再只用“报告是否变化”粗略判断有效率；
- supplementary search 最多选择 3 个结构化候选来源，模型只能输出 `{{SOURCE_n}}` 占位符；代码确定性分配引用编号、同步追加 `report.sources` 和“补充来源”条目，并拒绝模型自行生成的未知数字引用；
- 兼容模型输出 `[{{SOURCE_n}}]`，统一转换为单层 `[n]`，防止 `[[22]]`；self-verify 的局部上下文强制包含新增来源条目；
- Removal 从“删除片段”改为对最小完整句做 before/after 改写，降低 `，；`、残句和上下文断裂；
- self-verify 改为只审查本次变化附近的局部上下文，避免报告中未修改的旧问题误伤当前有效补丁。

真实后端回归先在 `tech_005 + fin_005` 上运行 v5，两个报告均产生正向 composite delta，平均 `+0.003677`、Win/Tie/Loss=`2/0/0`；其中 live 输出暴露了双层占位符问题并已修复。修复后对 `fin_005` 重跑 v6：单轮 5 个 issue 全部尝试，4 个提交、1 个回滚、0 个因熔断跳过，Critic 自评分 `4.825 → 5.325`；输出无 `[[数字]]` 引用，外部 composite delta 为 `+0.000025`。

这些结果证明有效修复率从该失败样本上的 `1/3` 提升到 `4/5`，且安全回滚仍生效；但 v5/v6 仅是针对性 smoke，样本过小，不能替代完整 21 题配对实验。产物位于 `outputs/evaluation/redblue-blue-repair-smoke-v5/` 和 `redblue-blue-repair-smoke-v6/`。

### Critic / Repairer / self-verify 上下文预算实验

原实现把 Critic 报告、Repairer 修复报告和 self-verify 变更上下文都硬编码为 4,000 字符。本轮将三者拆为独立配置，并设置 1,000–32,000 字符的防御性边界：

- `critic_context_chars`：默认由 4,000 提升到 8,000，让五维审查覆盖更多正文；
- `repairer_context_chars`：新增配置入口，但最终默认维持 4,000；
- `self_verify_context_chars`：由 4,000 提升到 6,000，仍然只发送局部 diff，并确保新增来源区进入验证上下文；
- 扩大上下文后，Repairer 不再因为“全文已装入 prompt”就无条件接受整篇 `fixed_content`，所有长度均优先要求精确 before/after patch；兼容整篇输出时仍必须保留原报告头尾锚点，避免增大预算同时扩大截断风险；
- runner 与 Critic-Repairer 配对实验脚本均从 `adversarial` 配置注入上述预算，后续更换异构模型时可分别调参，无需修改代码。

在同一 `fin_005` 上依次进行了三个 DeepSeek live smoke：

| 实验 | Critic / Repairer / Verify 字符预算 | Repairer 提交情况 | Critic 自评分 | 外部 Composite | 结论 |
|---|---:|---:|---:|---:|---|
| v7 | 8k / 8k / 6k | 3/5 | 4.55 → 5.475 | -0.007667 | Repairer 全文翻倍后修改偏多，citation coverage 下降 |
| v8 | 8k / 6k / 6k | 首轮 5/5；第二轮 0/2 | 4.55 → 5.9（首轮） | -0.019205 | 首轮过度提交并触发第二轮，整体状态 failed |
| v9 | 8k / 4k / 6k | 4/5 候选通过 | post-fix Critic 的 logical JSON 失败 | 0.0 | fail-closed，原报告未修改 |

因此没有把“更大上下文”直接作为 Repairer 的默认改进：8k 和 6k 在该样本上都劣于原 4k。最终采用 Critic 8k、Repairer 4k、局部 self-verify 6k，并保留独立配置开关。该结果也说明共享同一模型仍造成相关性判断、输出格式失败和 Critic 自评分与外部 citation 指标分歧；后续异构模型实验应基于独立配置继续做配对评估。

产物：`outputs/evaluation/redblue-context-smoke-v7/`、`redblue-context-smoke-v8/`、`redblue-context-smoke-v9/`。这些均为单题调参 smoke，不应并入正式效果统计。
